# Music Genre Classification using Machine Learning, Deep Learning, and DSP

This project is a completed SoftUni Machine Learning final project for music genre classification. It combines GTZAN and FMA Medium, harmonizes their labels into a shared seven-genre task, extracts MFCC and Mel Spectrogram features, trains classical and deep learning models, and evaluates post-training quantization for deployment.

## Project Goals

The goal is to compare compact DSP features and image-like spectrogram representations for genre classification under a realistic class imbalance. The project evaluates whether MFCC-based classical machine learning, a CNN trained from scratch, MobileNetV2 transfer learning, and quantized MobileNetV2 deployment variants can provide accurate and reproducible genre classification.

## Datasets

### GTZAN Genre Collection

Purpose: Primary dataset used for baseline experiments and model evaluation.

Download: GTZAN Genre Collection on Kaggle.

Download link:
https://www.kaggle.com/datasets/andradaolteanu/gtzan-dataset-music-genre-classification

The implementation expects GTZAN audio files under `data/raw/gtzan/genres/`, with one folder per genre.

### FMA Dataset

Purpose: Additional dataset used to improve dataset size and evaluate model generalization.

Download:

- `fma_medium.zip`
- `fma_metadata.zip`

Source: FMA Official Repository.

Download link:
https://github.com/mdeff/fma

The implementation expects FMA audio under `data/raw/fma_medium/` and metadata, including `tracks.csv`, under `data/raw/fma_metadata/`.

## Preparing the Dataset

The `data/` directory is intentionally excluded from Git because it contains large datasets and generated artifacts.

Before running the notebooks, create the following directory structure manually:

```text
data/
├── raw/
├── splits/
└── processed/
```

After downloading the datasets, place them as follows:

```text
data/
├── raw/
│   ├── gtzan/
│   │   └── genres/
│   ├── fma_medium/
│   └── fma_metadata/
│       ├── tracks.csv
│       ├── genres.csv
│       ├── features.csv
│       └── echonest.csv
├── splits/
└── processed/
```

The remaining directories are created automatically by the notebooks:

- **Notebook 02** generates:
  - `data/splits/train/`
  - `data/splits/validation/`
  - `data/splits/test/`

- **Notebook 03** generates:
  - `data/processed/mfcc/`
  - `data/processed/mel/`

No generated datasets need to be downloaded manually.

## Main Results

The final experiments show that the MFCC-based SVM is the strongest predictive model. The CNN and MobileNetV2 workflows reach similar accuracy on the imbalanced test set, but their macro F1 scores are lower because they perform poorly on several minority classes. Quantization is useful only when predictive performance is preserved; full static INT8 is not suitable here because it severely reduces macro F1.

| Model Family | Representative Model | Split | Accuracy | Macro F1 | Weighted F1 | Finding |
|---|---|---:|---:|---:|---:|---|
| Classical ML | SVM on MFCC | Test | 0.810 | 0.618 | 0.811 | Best overall macro F1. |
| CNN | Small CNN on Mel Spectrograms | Test | 0.813 | 0.384 | 0.766 | Stable but weak minority-class performance. |
| MobileNetV2 | Frozen ImageNet features | Test | 0.813 | 0.436 | 0.771 | Improves over CNN macro F1 but does not beat SVM. |
| Quantized MobileNetV2 | Dynamic Linear / classifier dynamic | Test | 0.813 | 0.439 | 0.772 | Preserves performance with small deployment benefit. |

Deployment trade-offs from Notebook 07:

| Variant | Size Reduction vs FP32 | Latency Reduction vs FP32 | Macro F1 |
|---|---:|---:|---:|
| Static INT8 core | 70.50% | 43.56% | 0.157 |
| Dynamic Linear | 0.28% | 0.93% | 0.439 |
| Classifier Dynamic | 0.27% | 1.05% | 0.439 |

The static INT8 model is smaller and faster but unsuitable because macro F1 drops sharply. Dynamic quantization variants preserve macro F1 within the project tolerance while providing modest CPU deployment benefits.

## Reproducibility

Generated datasets, trained models, and output reports are intentionally excluded from Git through `.gitignore`. This keeps the repository lightweight and avoids committing large generated artifacts.

They are recreated automatically by running the notebooks in order after placing GTZAN and FMA in the expected `data/raw/` directories. Paths, split settings, preprocessing parameters, and model artifact locations are centralized in `src/utils/config.py`.
